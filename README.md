# Transit Simulator

**街の移動を、デザインする。**

公共交通の利用状況と路線別収益を3D都市上で比較する、Webベースのシミュレーターです。
『Cities: Skylines』のような直感的な操作を入り口に、住民の移動のしやすさと交通事業者の持続可能性を一緒に考えられる作品を目指しています。

「公共交通オープンデータチャレンジ2026」への出展を開発目標としています。現在は、架空都市と仮定値を使って基本的な操作・計算を確認するMVP（最小限の動作モデル）です。

## 制作意義

公共交通の運行計画には、住民の利便性、運行費用、環境負荷など、同時に検討したい複数の観点があります。増便すれば待ち時間の短縮が期待できますが、人件費や燃料費も増えます。運賃の変更も、利用者の選択と事業収入の両方に影響します。

本作品では、こうした関係を設定変更と可視化によって理解できるようにします。路線の収支だけでなく、移動時間や公共交通の利用率も並べ、計画の利点と負担を比較するための材料を提供します。

想定する使い方は次のとおりです。

- **自治体・交通事業者の検討支援**：路線再編や運行条件の複数案を比較する。
- **住民との対話**：計画変更によって誰の移動が改善し、どのような費用が発生するかを共有する。
- **学習・体験**：都市づくりの感覚で、交通政策と経営の関係を学ぶ。
- **オープンデータの活用**：人口、移動需要、時刻表、都市モデルを結び付け、地域を理解する入口を作る。

将来的には、実際の地域を再現するデジタルツインとして育てます。そのために、データの出典と仮定を明示し、実測値との比較を通じて計算の妥当性を確認する方針です。

## 現在できること

| 機能 | 現在の内容 |
| --- | --- |
| 3D都市表示 | 架空の青葉市、3路線、模式的な建物・停留所・走行バスを表示 |
| 運行条件の変更 | バス運賃、運行間隔、渋滞倍率、移動する住民数を変更 |
| 移動手段選択 | 徒歩・自家用車・バス・鉄道をロジットモデルで比較 |
| ダッシュボード | 平均移動時間、公共交通利用率、バス純利益、推定CO₂削減量を表示 |
| 路線別収支 | 利用者数、運賃収入、運行費用、純利益を表示し、黒字を青・赤字を赤で色分け |
| シナリオ比較 | 現在の結果を保存し、変更後のバス純利益との差を表示 |
| GTFS変換 | GTFS ZIPからシミュレーター向けの軽量JSONを生成 |
| 経路探索の基礎 | 非負コストのグラフに対するA*を実装。画面の計算への接続は今後対応 |

GTFS変換JSONは、現時点では3D画面や需要計算に接続していません。PLATEAU、e-Stat、PT調査、ODPTの実データとの連携も今後の開発対象です。

## 使い方

### 1. 開発環境を準備する

- Node.js：Viteの実行要件に対応したバージョン。本プロジェクトはNode.js 26.11.1でビルド確認済みです。
- npm：Node.jsに付属するパッケージ管理ツール。
- Python：GTFS変換とPythonテストを実行する場合に使用。Python 3.13.5で確認済みです。
- WebGLに対応したブラウザ。

以下のコマンドは、プロジェクトのルートフォルダーで実行してください。Windows PowerShellでは `npm.cmd` を使います。macOS・Linuxでは `npm` に置き換えてください。

### 2. 起動する

初回は依存パッケージをインストールします。

```powershell
npm.cmd install
```

開発サーバーを起動します。

```powershell
npm.cmd run dev
```

ターミナルに表示されたローカルURLをブラウザで開いてください。終了する場合は、ターミナルで `Ctrl+C` を押します。

### 3. 都市と運行計画を操作する

1. 初期設定で、路線ごとの収支と移動手段の割合を確認します。
2. 「現在の結果を比較用に保存」を押し、比較の基準を残します。
3. 左側のスライダーで運賃・運行間隔・渋滞倍率・住民数を変更します。
4. 再計算された利用率・移動時間・収支を確認します。純利益の差は保存した結果を基準に表示されます。
5. 「初期設定に戻す」で運行条件をリセットできます。

たとえば、運行間隔を短くして、バス利用者の増加と運行費用の増加がどう釣り合うかを比較できます。

- マップをドラッグすると視点を回転できます。
- スクロールすると拡大・縮小できます。
- 「車両表示を一時停止」はバスのアニメーションだけを停止します。
- 比較用の保存はページを開いている間だけ有効です。再読み込みすると失われます。
- 保存前の純利益の比較基準は初期設定です。初期設定に戻しても、保存済みの比較基準は保持されます。

### 4. GTFSデータを変換する

入手したGTFS ZIPを、たとえば `data/feed.zip` に配置して実行します。

```powershell
python tools/gtfs_to_json.py data/feed.zip public/data/network.json
```

Pythonの標準ライブラリだけで実行できます。出力先のフォルダーは必要に応じて自動作成します。同じ出力ファイルがある場合は上書きします。

変換対象は停留所、路線、便、停車順序、路線形状、運行日、運賃、運行頻度、乗換規則です。
時刻は運行日午前0時からの秒数に変換し、`25:10:00` のような翌日扱いの時刻も保持します。未指定時刻は `null` として残します。

重複ID、不明な停留所・便・路線への参照、逆行する時刻などを検出すると変換を停止します。運賃がない場合は警告を表示します。GTFS全仕様を検証するバリデーターではありません。

変換したファイルを `public/data/` に置くだけでは、画面の表示データは切り替わりません。読み込み処理と時刻表に基づく経路探索は、次の開発段階で接続します。

## 今後の開発方針

最初に小さな対象地域でデータと計算をつなぎ、その後に都市の再現度と比較機能を高めます。以下は開発の優先順で、完了済み機能を示すものではありません。

### 第1段階：実際の交通ネットワークを表示する

- 対象地域と利用するデータセットを選定する。
- GTFS変換JSONを読み込み、実際の停留所と路線形状を表示する。
- 運行日判定、頻度便の展開、未指定時刻の補間を実装する。
- 区間運賃の照合と、欠損データを補うルールを整備する。

**到達目標：対象日の時刻表に沿った路線と便を、地図上で確認できる状態。**

### 第2段階：住民の移動を再現する

- e-Statの500mメッシュ人口を住民の初期配置に利用する。
- パーソントリップ（PT）調査を使い、属性別・時間帯別の移動需要を設定する。
- 道路網の経路探索と、待ち時間・乗換を含む公共交通の最早到着探索を接続する。
- 個々の住民の移動、車両定員、満員時の待機を扱うマルチエージェントモデルへ拡張する。
- 実際の利用者数などと比較し、移動手段選択モデルの係数を校正する。

**到達目標：住民の出発地・目的地・出発時刻に応じた移動を追跡できる状態。**

### 第3段階：路線変更の効果を比較する

- 路線の新設・再編、停留所配置、運行頻度を編集する機能を追加する。
- 車両保有数、回送、固定費、属性別割引を含めた収支計算を精緻化する。
- 交通空白地帯の解消度、属性別の移動改善、CO₂排出量を評価する。
- 複数シナリオの保存・読み込み・比較・結果出力を実装する。
- 人件費や需要の仮定を変え、結果がどの程度変動するか確認できるようにする。

**到達目標：住民の便益と事業収支を、複数の計画案で比較できる状態。**

### 第4段階：都市表現と出展品質を高める

- Project PLATEAUの3D都市モデルを取り込み、対象地域の景観を再現する。
- 必要に応じてGTFS-RTを取り込み、遅延や運行状況を反映する。
- データ量が増えても操作できるよう、描画と計算の負荷を改善する。
- 操作ガイド、デモシナリオ、出典表示、評価方法を整備する。
- コンテスト向けに、解決したい課題とシミュレーションの結果を説明できる作品に仕上げる。

**到達目標：初めて触る人が操作でき、結果の根拠も確認できるデモ。**

## 計算モデルと結果の読み方

現在の値は、モデルの動作を確認するための仮定です。実際の地域の需要・収益を予測する段階には達していません。

### 住民と移動手段選択

住民の属性構成は社会人60%、学生20%、高齢者20%を基本とし、出発時刻と移動距離を決定論的に生成します。1人につき1日1回の移動を計算します。

移動時間、運賃、時間価値、属性別の歩行ペナルティから効用を求めます。

```text
U = -0.08 × (移動時間 + 費用 / 時間価値 + 属性別歩行ペナルティ)
P(mode) = exp(U - max(U)) / Σ exp(U - max(U))
```

徒歩・車・バス・鉄道の選択確率を集計した期待人数を表示します。個々の住民が実際に乗車するイベントは未実装です。バス待ち時間は運行間隔の半分、停留所までと降車後の移動は合計8分と仮定しています。学生の運賃は20%引き、高齢者は50%引きです。

### 路線別収支

```text
収入 = 割引後運賃 × 期待乗車人数
走行距離 = 区間長 × 便数（16時間運行・両方向）
費用 = 走行距離 / 22km/h × 渋滞倍率 × 2,400円/時
     + 走行距離 × 45円/km
     + 固定費9,200円/路線・日
純利益 = 収入 - 費用
```

現在は車両定員、回送、車両保有数、詳細な区間運賃を扱っていません。路線の赤字表示は、この仮定における収支を示します。路線の必要性を判断する際は、移動改善や地域へのサービスも併せて評価する方針です。

### 移動改善とCO₂

平均移動時間の短縮とCO₂削減量は、公共交通がない場合に徒歩・車から再選択するモデルと比較します。

CO₂排出係数は、車0.17、バス0.06、鉄道0.025 kg/人kmと仮定しています。バスは平均的な人kmあたりの概算で、運行便数や乗車率に応じた車両単位の排出計算は未実装です。

住民の便益は現在、平均移動時間の短縮として表示します。幸福度スコアと交通空白地帯の評価は今後実装します。3Dの車両アニメーションは運行を示す模式表示です。

## 開発・検証

```powershell
# 型チェックと本番用ビルド
npm.cmd run build

# 静的解析
npm.cmd run lint

# ロジットモデル・経路探索・収支計算のテスト
node --test tests/simulation.test.ts

# GTFS変換のテスト
python -m unittest discover -s tests -v

# ビルド済み画面のローカル確認
npm.cmd run preview
```

自動テストに加えて、ブラウザで3D描画、操作、画面幅によるレイアウトを確認してください。現在のビルドではThree.jsなどを含むバンドルのサイズ警告が出ます。読み込み時間の改善は今後の課題です。

### 主なファイル

| ファイル | 役割 |
| --- | --- |
| `src/App.tsx` | 3D都市、運行設定、結果ダッシュボード |
| `src/simulation.ts` | ロジットモデル、A*、需要と収支の計算 |
| `src/App.css` / `src/index.css` | 画面レイアウトと基本スタイル |
| `tools/gtfs_to_json.py` | GTFS ZIPからJSONへの変換 |
| `tests/simulation.test.ts` | シミュレーション計算の検証 |
| `tests/test_gtfs.py` | GTFS変換の検証 |

技術構成はReact、TypeScript、Three.js、React Three Fiber、Drei、Viteです。データ変換にはPythonを使います。A*は非負コストのグラフ用で、既定のヒューリスティック0ではDijkstraとして動作します。現在の画面は距離・速度の仮定から時間を計算しており、経路探索は未接続です。

## データ利用の方針

実データを導入するときは、出典、ライセンス、取得日、対象地域、対象運行日、欠損補完方法を記録します。調査から得た値と、開発上の仮定を区別して表示します。APIキーなどの認証情報はリポジトリへ保存しません。

GTFSの変換設計では、[GTFS Schedule公式リファレンス](https://gtfs.org/documentation/schedule/reference/)を参照しています。実運賃の照合、Fares v2、GTFS-RTへの対応は今後追加します。
